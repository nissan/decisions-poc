# Experiment: Subagent Routing Adviser

**Hypothesis:** On the same synthetic planning tasks, a typed decision model can improve on current Workbench task analysis and model selection: recover an avoidable review or recommend a less costly acceptable lane without regressing on a correct decision. A lane is one exact `(provider, model, reasoning level)` tuple. The [comparison matrix](providers.md) includes three typed APIs and ordinary generative LLM controls. Optimize useful work per budget, not tokens consumed. **Draft:** the maintainer reviews scenarios, baseline procedure and pass criteria before the holdout.

## Smallest useful application

One Python CLI scores a synthetic task packet containing outcome, acceptance checks, dependencies, constraints and required tools. A separate trusted fixture defines the approved lane catalog, capability matrix, simulated quota/capacity, and remaining budget. Use four or five synthetic provider/model/effort tuples, including two effort levels for one model. Keep model price and estimated input, output, and billed reasoning tokens separate. No access to candidate executor accounts, task execution, agents, scheduler, project tracker access or settings mutation. Decision models are classifiers, not candidate executors.

1. **Filter in code.** Resolve approved aliases. Exclude lanes missing capability, policy authorization, known quota, a provider-family slot, or budget under a conservative cost estimate. Unknown global policy/budget or no eligible lane means `review`; automation skips the model call. This filter is for the experiment, not a claim about the current Workbench runtime.
2. **Score the task, not the permissions.** Give comparison arms the same original synthetic task text and eligible candidates, with their capabilities and relative cost ranks plus a `review` option. Do not send gold labels or a preclassified work-type hint to any model or baseline planner. The old static rule diagnostic may use its existing fixture hint and is reported separately. One request asks three independent questions; a task cannot authorize a lane.
3. **Apply policy in code.** Every automation arm rejects out-of-policy lane IDs and malformed replies and cannot dispatch. Typed arms require selected-lane probability ≥0.80 and `P(task_clear=yes)` ≥0.75; classic arms use explicit clarity and abstention fields. Report these operational results as well as a common categorical comparison. A provider error is not an abstention or a cue to fall back.

| Question ID | Type | Criteria |
| --- | --- | --- |
| `lane_fit` | `choice` | Choose the least costly eligible lane that meets the task's requirements; use `review` for unresolved ambiguity or no sound fit. |
| `task_clear` | `noul` / `predicate` | Is the task sufficiently scoped to choose an executor, with an outcome and verifiable acceptance? |
| `complexity` | `score` | 0 mechanical; 1 bounded but requires judgment; 2 multi-step or ambiguous with material tradeoffs. Show the distribution; advisory only. |

## Primary baseline: current Workbench planning workflow

The baseline is the **current planner and operator's normal task analysis and selection**, not the POC's rule function and not a newly prompted model. Apply the approved operating practice: classify work type, complexity, uncertainty and risk; choose the normal role/tier and reasoning; resolve approved model aliases; check actual eligibility against the fixture's synthetic authorization, capabilities, quota, capacity and budget; record a proposed tuple or review. Continue to use the normal human gate where it exists. Do not actually dispatch.

Freeze the baseline environment and input: planner/harness identity and model/effort if assisted, policy/adapter revision and digest, synthetic lane mapping, and permitted context. Use the ordinary planning process in a synthetic-only workspace, with no fixtures that reveal gold labels, no held-out outputs from other arms, and no substituted heuristic. Before running the other arms on holdout, record the first submitted result per case, its grounds, whether a human changed the choice, duration including human time, and any available (not guessed) model usage. Keep the baseline's original recommendation and separately mark any violation; do not silently fix it. If current practice cannot be reproduced on synthetic tasks, call the primary comparison inconclusive rather than elevating the diagnostic rules.

The existing offline rule arm is retained as a **diagnostic control**. Its historic run was on the draft corpus, not a measurement of current Workbench practice.

## Paired evaluation

1. Retain the development cases and prepare a fresh 24-case holdout with disjoint scenarios. The old draft holdout exposed its labels in the public branch and is usable only for diagnostics. An independent labeler records acceptable tuples or `review` and why; commit a digest of that private label file before runs and release labels only after all outputs are locked. Freeze eligible-lane policy, prompts, models/efforts, thresholds, ordering and forecast assumptions before holdout.
2. Capture the current-practice baseline first and post its byte digest on #4 before any comparator holdout run. Each comparator receipt records the precommitted label and baseline digests and the frozen configuration ID. Compare each configuration against that same baseline on the same cases. The static rules are diagnostic only, and direct provider-vs-provider pairings are secondary.
3. Report acceptable and wrong recommendations, eligible-case coverage, necessary and avoidable review, policy violations, failures, and baseline-relative paired gains and regressions. Compare projected executor cost only where both methods routed acceptably. Keep that forecast separate from the router's input/output/reasoning usage, entitlement consumption and elapsed time. For the shared categorical view, map native clarity to `yes` only when `P(yes) > 0.5`; negative/uncertain clarity or an explicit abstention means `review` for every arm. Separately report each full policy's coverage/error tradeoff. Do not equate a classic model's stated confidence with a native probability.
4. Draft pass rule for each configuration versus current practice: zero ineligible published suggestions, no regression where the current planner was correct (including correct reviews), and at least two cases where the comparator recovers an avoidable review or recommends a less costly acceptable lane. Missing runs make that comparison inconclusive. This synthetic study does not measure downstream quality or realized savings.

## Evidence gates

- Offline: `python3 -m unittest discover -s tests -v`. Exercise eligible selection, both forms of review, high-confidence **no**, unknown or exhausted admission, a disallowed provider, budget exhaustion, malformed response and HTTP failure. No live API in deterministic checks.
- Live: smoke each configuration using the same synthetic development packet and an approved no-additional-spend path. Confirm exact served model, effort, schema and available usage fields. Then collect the current-practice baseline and run the frozen holdout after maintainer review. Stop on unexpected billing, fallback, or admission errors. Do not treat subscription allowance or a sponsored gateway as an API entitlement or a permanent price.
- Delivery: use a standalone native workspace and a small branch/PR from the default head. Self-review the exact head and attach actual check evidence before owner acceptance or merge. No hosted check configured at kickoff. This experiment informs a possible Workbench decision-provider evaluation; it does not implement or close Workbench product work.
